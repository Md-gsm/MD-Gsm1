# 1. هدف و جایگاه

## 1.1 هدف

این سند مرجع یکپارچه کنترل و تطبیق سه حوزه زیر است:

- 7B — Master Posting Matrix
- 7C — Chart of Accounts Reconciliation
- 7D — Test-to-FE/COA Reconciliation Register

هدف، ایجاد زنجیره قابل ردیابی میان رویداد مالی، قاعده شناسایی، قاعده ثبت، حساب دفتر کل، زیرمعین، آزمون و شواهد پذیرش است.

زنجیره مرجع:

Financial Event → Recognition Rule → Posting Rule → COA → Subledger → Test Case → Evidence

برای هر رویداد باید بتوان مشخص کرد:
1. رویداد از کدام منبع ایجاد شده است؟
2. چه زمانی از نظر مالی قابل شناسایی است؟
3. چه پیش‌شرط‌هایی برای ثبت لازم است؟
4. کدام حساب بدهکار و کدام حساب بستانکار می‌شود؟
5. مبلغ و بهای تمام‌شده بر چه مبنایی محاسبه می‌شوند؟
6. چه زیرمعین‌ها و ابعادی باید به‌روزرسانی شوند؟
7. چه محدودیت مالیاتی یا عملیاتی وجود دارد؟
8. Retry و Duplicate چگونه کنترل می‌شوند؟
9. برگشت یا اصلاح سند چگونه انجام می‌شود؟
10. کدام آزمون‌ها رفتار را کنترل می‌کنند و چه شواهدی لازم است؟

## 1.2 محدوده

این سند فقط مرجع طراحی و کنترل اسناد 7B، 7C و 7D در حوزه مالی است. این سند به‌تنهایی مجوز پیاده‌سازی موتور مالی، ایجاد migration، اجرای ثبت واقعی یا فعال‌سازی ماژول Accounting نیست.

# 2. حاکمیت منابع و تعارض

## 2.1 سلسله‌مراتب اعتبار

در صورت مشاهده تعارض، ترتیب اعتبار به شرح زیر است:

1. تصمیم صریح و نهایی مالک در دامنه ثبت‌شده؛
2. ADR پذیرفته‌شده؛
3. متن هنجاری سند معماری مرجع v2.5؛
4. منبع اصلی قابل احراز حساب‌ها و اسناد مالی؛
5. اسناد مستقل بازسازی‌شده 7B، 7C و 7D؛
6. پیشنهادهای مهندسی.

تصمیم نهایی مالک نباید دوباره برای تصویب مطرح شود. اگر مانع اجرایی واقعی، تعارض مستند یا شواهد جدید وجود داشت، مسیر رسیدگی Change Request است.

## 2.2 طبقه‌بندی منشأ

| Source Class | مفهوم |
|---|---|
| OWNER_DECISION | تصمیم صریح مالک |
| ADR | تصمیم معماری ثبت‌شده |
| ARCHITECTURE_BASELINE | قاعده سند معماری |
| PRIMARY_SOURCE | داده استخراج‌شده از منبع اصلی |
| RECONSTRUCTED | بازسازی کنترل‌شده از منابع ناقص |
| PROPOSED | پیشنهاد جدید و تأییدنشده |
| NOT_VERIFIED | منشأ یا صحت هنوز احراز نشده |

هیچ داده PROPOSED یا NOT_VERIFIED نباید به‌عنوان مقدار قطعی در موتور مالی استفاده شود.

## 2.3 واژگان هنجاری

- MUST: الزام قطعی.
- MUST NOT: ممنوعیت قطعی.
- SHOULD: توصیه قوی؛ عدول نیازمند توجیه مستند است.
- MAY: اختیار مجاز در چارچوب سایر قواعد.
- OPEN: بررسی یا تصمیم فنی تکمیل نشده است.
- BLOCKED: اجرای رفتار تا رفع مانع ممنوع است.
- NOT VERIFIED: صحت یا اجرا با شواهد اثبات نشده است.

# 3. اصول پایه مالی

## 3.1 عدم ثبت بر اساس حدس

سیستم MUST NOT برای تکمیل ثبت، حساب بدهکار یا بستانکار را بر اساس شباهت عنوان، شماره حساب یا حدس مهندسی انتخاب کند.

اگر حساب مقابل، ماهیت اقتصادی، مبلغ یا شرط شناسایی مشخص نیست، ثبت باید Fail Closed شود.

## 3.2 تفکیک رویدادها

موارد زیر رفتارهای مستقل‌اند و نباید بدون قاعده در یک ثبت مبهم ادغام شوند:

- صدور فاکتور؛
- دریافت فیزیکی کالا؛
- دریافت خدمت؛
- دریافت وجه؛
- تخصیص وجه؛
- شناسایی درآمد؛
- تحویل کالا یا خدمت؛
- خروج موجودی؛
- برگشت وجه؛
- برگشت کالا؛
- اصلاح یا برگشت سند.

یک رویداد عملیاتی ممکن است چند اثر مالی مستقل داشته باشد؛ هر اثر باید منشأ و Posting Identity قابل ردیابی داشته باشد.

## 3.3 دریافت وجه مساوی درآمد نیست

دریافت وجه به‌تنهایی مجوز شناسایی درآمد نیست. ماهیت دریافت باید مشخص شود؛ از جمله پیش‌دریافت، دریافت بابت بدهی قبلی، دریافت تخصیص‌نیافته یا دریافت مرتبط با درآمد تحقق‌یافته.

## 3.4 تفکیک بدهی‌ها

| کد | مفهوم |
|---|---|
| 2101 | بدهی فاکتورشده به تأمین‌کننده |
| 2103 | کالای دریافت‌شده ولی فاکتورنشده |
| 2114 | خدمت دریافت‌شده و تأییدشده ولی فاکتورنشده |

این مفاهیم مستقل‌اند و قابل جایگزینی نیستند.

## 3.5 ثبت اتمیک

عملیات مالی و تغییرات مرتبط در موجودی، دریافت و پرداخت یا سایر منابع مالی باید مطابق قرارداد تراکنش اتمیک انجام شوند.

سیستم MUST NOT وضعیتی ایجاد کند که:
- ثبت مالی موفق شود ولی حرکت موجودی الزامی شکست بخورد؛
- حرکت موجودی ثبت شود ولی اثر مالی الزامی از بین برود؛
- Retry موجب ثبت دوباره شود؛
- شکست میانی وضعیت غیرقابل بازیابی ایجاد کند.

## 3.6 اصلاح اسناد نهایی‌شده

اسناد مالی نهایی‌شده نباید با تغییر پنهانی داده‌های تاریخی اصلاح شوند. اصلاح باید از طریق سند اصلاحی، برگشت یا فرآیند مجاز و قابل ردیابی انجام شود.

## 3.7 رویداد ناشناخته

رویداد فاقد Posting Rule معتبر باید Fail Closed شود. سیستم MUST NOT آن را به حساب عمومی، حساب موقت نامرتبط یا حسابی با عنوان مشابه منتقل کند.

# 7. سیاست محاسبات پولی و ADR-0017

## 7.1 تصمیم قطعی

ADR-0017 سیاست integer-only را تثبیت کرده است:
- واحد پایه و ذخیره‌سازی پول IRR است.
- تمام مبالغ پولی از ورودی تا خروجی عدد صحیح علامت‌دار هستند.
- هیچ مبلغ پولی میانی اعشاری یا کسری ریال مجاز نیست.
- نرخ‌ها و نسبت‌های غیرپولی در صورت نیاز به شکل کسر صحیح صورت/مخرج نگهداری می‌شوند.
- تبدیل خروجی عملیات نسبتی به مبلغ صحیح با AwayFromZero انجام می‌شود.
- ورودی مبلغ IRR اعشاری، مبهم یا خارج از دامنه رد می‌شود؛ گردکردن، truncate و clamp ورودی ممنوع است.
- تخصیص تجمیعی با largest remainder قطعی و tie-break پایدار انجام می‌شود.
- برگشت کامل باید مبلغ صحیح نهایی سند مبدأ را دقیقاً معکوس کند؛ برگشت جزئی تابع قرارداد تخصیص نسخه‌دار است.

## 7.2 سقف اثر گرد کردن

سقف مالک در سطح سند به‌صورت مقایسه خروجی integer-only نهایی با مرجع rational دقیق همان فرمول سند تعریف شده است:

|R - N/D| ≤ 1 IRR

این قاعده به معنی مجاز بودن ذخیره یا Posting مبلغ کسری ریال نیست. مرجع rational فقط معیار کنترل و آزمون غیرپولی است. اگر مرجع دقیق یا ورودی‌های لازم برای بازسازی فرمول سند در دسترس نباشد، مسیر باید Fail Closed شود.

نباید این قاعده به «تلورانس عمومی یک ریال برای هر خط»، «گرد کردن صرفاً در جمع نهایی» یا مجوز ثبت کسری ریال تعبیر شود.

## 7.3 مقدار 100,000 IRR per line

معنای مستقل مقدار 100,000 IRR per line در ADR-0017 باز است و هنوز احراز نشده است. این مقدار:
- سقف گرد کردن نیست؛
- تلورانس یک ریالی سند نیست؛
- مجوز اختلاف قیمت نیست؛
- نباید در هیچ محاسبه یا کنترل گرد کردن استفاده شود.

وضعیت آن OPEN — SOURCE/OWNER MEANING NOT VERIFIED باقی می‌ماند.

## 7.4 حساب‌های 4107 و 5106

4107 فقط سود و 5106 فقط زیان گرد کردن است. هیچ Journal خودکاری تا تکمیل موارد زیر مجاز نیست:
- COA collision check؛
- Normal Side و ویژگی‌های حساب؛
- Posting Matrix صریح؛
- Posting Identity و idempotency؛
- علت و سند مرجع؛
- آزمون‌های مربوط.

ADR-0017 به‌تنهایی مجوز ثبت در این حساب‌ها نیست.

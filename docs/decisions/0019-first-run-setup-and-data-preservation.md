# ADR-0019 — راه‌اندازی اولیهٔ یک‌باره و حفظ داده در نصب مجدد و ارتقا

- **وضعیت:** پذیرفته‌شده در سطح سیاست محصول و قیود معماری؛ پیاده‌سازی و Gate D باز است.
- **تاریخ تصمیم:** 2026-11-23
- **مالک تصمیم:** Product Owner پروژه (همان مالک فعلی؛ بدون افزودن شخص یا عضو جدید)
- **دامنه:** Platform Operations، نصب Windows Server/Desktop، IdentityAccess، Organization و Accounting
- **منابع حاکم:** ADR-0003، ADR-0012، سیاست تغییر دیتابیس و migrationها، قواعد persistence و migrations، IdentityAccess Module Baseline و ممیزی O-46

## 1. مسئله

راه‌اندازی اولیه باید اطلاعات مالک، کارگاه و اولین دورهٔ مالی را فقط برای یک استقرار واقعاً جدید دریافت کند. نصب مجدد فایل‌های برنامه، تعمیر نصب، تعویض نسخه یا ارتقای نرم‌افزار نباید به‌اشتباه به‌عنوان استقرار جدید تشخیص داده شود. در غیر این صورت خطر ساخت حساب مالک دوم، تغییر اتصال به پایگاه خالی، تکرار دورهٔ مالی یا از دست رفتن سابقهٔ عملیاتی و مالی وجود دارد.

MD-Gsm از یک پایگاه دادهٔ مرکزی و دائمی استفاده می‌کند و سال مالی یک موجودیت مستقل در همان پایگاه است؛ پایگاه جداگانه برای هر سال ساخته نمی‌شود. بنابراین چرخهٔ عمر فایل‌های اجرایی برنامه از چرخهٔ عمر دادهٔ کسب‌وکار جداست.

## 2. تصمیم‌ها

### 2.1 تفکیک سه وضعیت نصب

1. **استقرار تازه و واقعاً بدون راه‌اندازی:** فقط وقتی مجاز است Wizard اولیه آغاز شود که سرور به یک پایگاه دادهٔ جدید و مشخص‌شده برای همین استقرار متصل باشد و وضعیت معتبر و پایدار راه‌اندازی، `NotStarted` را نشان دهد. تشخیص «جدید بودن» صرفاً از روی خطای اتصال، خالی بودن چند جدول، نبود فایل تنظیمات یا ناموفق بودن احراز هویت مجاز نیست.
2. **نصب مجدد، Repair یا تعویض فایل‌های اجرایی:** باید همان پیکربندی پایدار و همان پایگاه دادهٔ مرکزی قبلی را نگه دارد. پس از اتصال موفق، برنامه مستقیماً وضعیت موجود را می‌خواند و به صفحهٔ ورود می‌رود؛ Wizard مالک/کارگاه/سال مالی دوباره اجرا نمی‌شود.
3. **ارتقای نسخه:** فقط فایل‌های اجرایی و در صورت نیاز، مسیر migration نسخه‌دار و تأییدشده تغییر می‌کند. ارتقا پایگاه تازه، حساب مالک تازه، کارگاه تازه یا دورهٔ مالی تازه ایجاد نمی‌کند.

نصب Desktop روی رایانهٔ دوم یا بعدی، نصب مستقل یک کسب‌وکار نیست؛ کلاینت باید به سرور مرکزی از قبل راه‌اندازی‌شده متصل شود و هرگز Wizard ایجاد مالک یا دورهٔ مالی را اجرا نکند.

### 2.2 رفتار fail-closed در تشخیص وضعیت

- اگر پایگاه داده در دسترس نیست، اتصال نامعتبر است، پیکربندی لازم پیدا نمی‌شود یا هویت پایگاه قابل اثبات نیست، برنامه باید خطای روشن و قابل عیب‌یابی بدهد و متوقف شود؛ نباید پایگاه خالی تازه بسازد یا Wizard را به‌عنوان راه‌حل جایگزین نمایش دهد.
- اگر نسخهٔ schema ناشناخته، ناسازگار، ناقص یا در وضعیت migration نیمه‌تمام باشد، برنامه باید به مسیر نگهداری/بازیابی کنترل‌شده برود؛ نه اینکه نصب تازه یا seed اولیه را آغاز کند.
- وضعیت راه‌اندازی باید پایدار و قابل بازیابی باشد. بعد از قطع برق یا بسته‌شدن برنامه در میانهٔ Wizard، اجرای مجدد باید همان عملیات را ادامه دهد و مرحله‌های موفق را تکرار نکند.

### 2.3 Wizard فقط یک بار و با مالکیت تفکیک‌شدهٔ ماژول‌ها

Wizard اولیه یک هماهنگ‌کننده است و مالک داده‌های تجاری هیچ‌یک از ماژول‌ها نمی‌شود:

- **IdentityAccess:** ایجاد حساب اولیهٔ مالک، اعتبارنامه و اتصال غیرقابل‌انتقال Product Owner به همان `AccountId`.
- **Organization:** ثبت هویت و مشخصات کارگاه/کسب‌وکار.
- **Accounting:** ایجاد دقیقاً یک دورهٔ مالی اولیه با بازه‌ای که مالک تعیین می‌کند.
- **Platform Setup Orchestrator:** نگه‌داری صرفاً وضعیت فنی و پیشرفت گام‌های راه‌اندازی، شناسهٔ عملیات پایدار و نتیجهٔ هر گام؛ بدون مالکیت Account، اطلاعات کارگاه یا FiscalPeriod.

هر ماژول تغییر دادهٔ خود را در تراکنش محلی خودش انجام می‌دهد. هماهنگ‌کننده از عملیات idempotent و شناسهٔ عملیات ثابت برای ادامه پس از شکست استفاده می‌کند؛ تراکنش توزیع‌شدهٔ واحد میان ماژول‌ها فرض نمی‌شود. وضعیت کلی فقط پس از ثبت و راستی‌آزمایی موفق تمام گام‌های لازم `Completed` می‌شود. تا آن زمان مسیرهای عادی کسب‌وکار و دسترسی شبکه‌ایِ غیرضروری باید بسته بمانند.

هیچ حساب ثابت یا قابل حدس مانند `admin/admin`، رمز مشترک، رمز جاسازی‌شده در installer/source، یا credential چاپ‌شده در log مجاز نیست. روش دقیق احراز اختیار آغاز Wizard، مرز اعتماد محلی، تحویل/ثبت امن اعتبارنامهٔ اولیه و کنترل‌های ضدتکرار همچنان تابع تکمیل ممیزی O-46 است و این ADR به‌تنهایی آن جزئیات را تصویب نمی‌کند.

### 2.4 دوره‌های مالی

- Wizard فقط دورهٔ مالی اولیه را در استقرار واقعاً جدید ایجاد می‌کند.
- دوره‌های مالی سال‌های بعد صرفاً از قابلیت مدیریت دوره‌های مالی در Accounting و با کنترل‌های همان ماژول ایجاد می‌شوند؛ نه با نصب مجدد، ورود مجدد، ارتقای نسخه یا شروع سال تقویمی جدید.
- بستن یا ایجاد دورهٔ مالی جدید، سوابق سال‌های گذشته، اشخاص، مشتریان، تعمیرات، اسناد، موجودی یا ارتباطات تاریخی را پاک، کپی یا بازسازی نمی‌کند.
- آغاز سال جدید به‌خودی‌خود مجوز ثبت افتتاحیه نیست. افتتاحیه طبق سیاست حسابداری و فقط یک بار، با تطبیق‌های مقرر انجام می‌شود.

### 2.5 مرز دادهٔ پایدار و فایل‌های برنامه

- فایل‌های اجرایی، shortcutها و اجزای قابل جایگزینی برنامه باید از پایگاه داده، فایل‌های پیوست/مدارک، تنظیمات پایدار، ارجاع‌های کلید/راز و نسخه‌های پشتیبان جدا نگه داشته شوند.
- دادهٔ کسب‌وکار نباید در پوشه‌ای قرار گیرد که installer یا uninstaller آن را به‌عنوان مقصد حذف/جایگزینی فایل‌های برنامه مدیریت می‌کند.
- Update، Repair و Uninstall عادی فقط مجاز به تغییر/حذف اجزای برنامه هستند؛ نباید پایگاه PostgreSQL، schema/data، فایل‌های کسب‌وکار، پیوست‌ها، تنظیمات اتصال، کلیدهای لازم برای خواندن دادهٔ رمز‌شده یا backupها را حذف یا بازنشانی کنند.
- حذف عمدی داده باید عملیات جداگانه، صریح، محدود به دامنهٔ مشخص، دارای مجوز مالک، بررسی نگهداری قانونی، پشتیبان قابل‌بازیابی و ثبت audit باشد. این عملیات بخشی از uninstall یا update عادی نیست.
- کلاینت‌های Windows منبع حقیقت دادهٔ تجاری نیستند؛ نصب مجدد یک کلاینت نباید بر دادهٔ سرور مرکزی اثر بگذارد.

### 2.6 ارتقای schema و حفاظت از داده

- سیاست موجود پابرجاست: API در startup migration اجرا نمی‌کند؛ migration از مسیر صریح و با هویت deployment مجزا اجرا می‌شود.
- پیش از هر ارتقای داده‌محور، پایگاه هدف، شناسهٔ استقرار، نسخهٔ schema و مسیر ترتیبی migration باید بررسی شوند. checksum/name drift، نسخهٔ مفقود، نسخهٔ ناشناخته یا مقصد اشتباه، ارتقا را متوقف می‌کند.
- پیش از migration تولیدی، backup پایگاه و فایل‌های وابسته باید تهیه و قابلیت restore آن در محیط جداگانه اثبات شود. اگر backup/restore معتبر در دسترس نیست، migration داده‌محور متوقف می‌شود.
- migrationهای اعمال‌شده بازنویسی نمی‌شوند. تغییر schema با migration جدید، نسخه‌دار، بررسی‌شده و آزموده‌شده انجام می‌شود. migration باید تا حد مجاز اتمیک باشد؛ شکست عملیات غیراتمیک باید runbook بازیابی مشخص داشته باشد.
- حذف/بازسازی schema، `DROP`، `TRUNCATE` یا پاک‌سازی/seed مجدد دادهٔ موجود بخشی از مسیر استاندارد update نیست. هر تغییر بالقوه مخرب به بررسی اثر داده، مجوز مستقل، برنامهٔ بازیابی و آزمون حفظ تاریخچه نیاز دارد؛ برای داده‌های مالی و امنیتی مسیر اصلاحی forward ترجیح دارد و downgrade مخرب پیش‌فرض نیست.
- اگر migration شکست بخورد، برنامه باید ارتقا را متوقف کند و دادهٔ قبلی را حفظ کند؛ reset خودکار، اتصال خودکار به دیتابیس خالی یا اجرای دوبارهٔ Wizard ممنوع است.
- backup و مواد کلیدی لازم برای بازیابی دادهٔ رمز‌شده باید با هم مدیریت شوند؛ backup بدون امکان بازیابی کلیدهای لازم، اثبات بازیابی کامل محسوب نمی‌شود.

### 2.7 حفظ هویت مالک و وضعیت راه‌اندازی

- حساب اولیهٔ مالک، `AccountId` و Product Owner binding در پایگاه مرکزی نگه‌داری می‌شوند و با نصب/حذف فایل‌های اجرایی دوباره ایجاد یا جایگزین نمی‌شوند.
- reinstall/update نباید username/password، نقش‌ها، وضعیت دسترسی، شناسهٔ مالک، شناسهٔ کارگاه، شناسهٔ دوره‌های مالی یا وضعیت تکمیل راه‌اندازی را reset کند.
- بازیابی پایگاه از backup باید همان هویت‌ها، پیوندها، وضعیت تکمیل راه‌اندازی و سابقه را بازیابی کند؛ پس از restore موفق، Wizard اولیه دوباره نمایش داده نمی‌شود.

## 3. مواردی که هنوز باز هستند

این تصمیم رفتاری محصول و قیود حفظ داده را می‌پذیرد، اما موارد زیر برای پیاده‌سازی هنوز باید طراحی و مستقلاً بررسی شوند:

1. مرز اعتماد و مجوز اجرای Wizard فقط روی میزبان سرور، اثبات حضور/اختیار محلی و کنترل آغاز راه‌اندازی.
2. قرارداد دقیق bootstrap، credential handling و ثبت Account اولیه طبق O-46؛ شامل idempotency و رفتار commit مبهم.
3. محل و قالب پایدار تنظیمات سرور، شناسهٔ استقرار، دادهٔ پیوست‌ها و ارجاع به کلیدها؛ با حفظ جداسازی فایل اجرایی از داده.
4. state machine و قرارداد persistence هماهنگ‌کنندهٔ راه‌اندازی، بدون نقض مالکیت ماژول‌ها.
5. سیاست سازگاری نسخهٔ API/Desktop در ارتقای چند رایانه و رویهٔ migration/forward-fix/restore.
6. RPO/RTO و شواهد عملی backup/restore هماهنگ پایگاه، فایل‌ها و کلیدها.
7. فهرست نهایی فیلدهای Wizard و اعتبارسنجی تقویم/بازهٔ دورهٔ مالی بر اساس قرارداد Accounting.

هیچ‌یک از این موارد نباید با حدس در کد، schema، migration یا installer تثبیت شود.

## 4. معیارهای پذیرش اجباری برای Gate D

| شناسه | سناریو | نتیجهٔ مورد انتظار |
|---|---|---|
| SETUP-01 | نصب تمیز روی پایگاه تازه و مجاز | Wizard یک بار اجرا و مالک/کارگاه/دورهٔ اولیه هرکدام دقیقاً یک بار ایجاد شوند. |
| SETUP-02 | restart پس از تکمیل راه‌اندازی | ورود عادی؛ بدون Wizard و بدون ایجاد رکورد تکراری. |
| SETUP-03 | قطع فرایند در هر مرحلهٔ Wizard | ادامه از وضعیت پایدار؛ بدون مالک، کارگاه یا دورهٔ تکراری. |
| SETUP-04 | نصب مجدد یا Repair فایل‌های برنامه با همان پایگاه | همهٔ داده‌ها و شناسه‌ها حفظ شوند؛ Wizard نمایش داده نشود. |
| SETUP-05 | ارتقای نسخه روی پایگاه موجود | داده و تنظیمات حفظ شوند؛ فقط migrationهای لازم و مجاز اجرا شوند؛ هیچ دورهٔ جدیدی ساخته نشود. |
| SETUP-06 | نصب کلاینت دوم/بعدی | اتصال به سرور موجود و نمایش ورود؛ عدم ایجاد owner/workshop/fiscal period. |
| SETUP-07 | قطع اتصال یا پیکربندی ناقص | خطای fail-closed؛ عدم ساخت پایگاه خالی و عدم نمایش Wizard جایگزین. |
| SETUP-08 | schema نامعتبر یا migration ناموفق | توقف کنترل‌شده؛ بدون reset، seed مجدد یا حذف داده. |
| SETUP-09 | restore backup | حفظ AccountId، Product Owner binding، اطلاعات کارگاه، دوره‌ها، تنظیمات و فایل‌های وابسته؛ عدم تکرار Wizard. |
| SETUP-10 | uninstall عادی | حذف فایل‌های برنامه/shortcutها؛ حفظ DB، پیوست‌ها، تنظیمات پایدار، کلیدهای لازم و backupها. |
| SETUP-11 | ایجاد سال مالی بعدی | انجام از Accounting؛ حفظ دوره‌ها و سوابق قبلی؛ عدم دخالت installer یا Wizard. |
| SETUP-12 | چند نسخهٔ Desktop هم‌زمان با سرور ارتقایافته | سازگاری طبق ماتریس نسخهٔ تأییدشده؛ عدم نوشتن دادهٔ تجاری روی کلاینت. |

هر آزمون باید با دادهٔ مصنوعیِ قابل‌شمارش و شناسه‌های قبل/بعد قابل‌تطبیق اجرا شود؛ آزمون روی پایگاه واقعیِ دارای دادهٔ ارزشمند یا reset آن برای اثبات قبولی ممنوع است.

## 5. محدودیت مجوز

این ADR به‌تنهایی مجوز اجرای bootstrap واقعی، ایجاد حساب/role/permission/seed، افزودن schema یا migration، فعال‌سازی endpoint یا network listener، تغییر production database، حذف داده، صدور G1، تکمیل O-46 یا Go-Live نیست. پیاده‌سازی پس از بستن موارد باز، بازبینی امنیتی مستقل، آزمون‌های Gate D و پذیرش شواهد exact-head و release gate مربوط مجاز خواهد بود.

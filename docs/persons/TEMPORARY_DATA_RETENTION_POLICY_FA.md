# سیاست عملیاتی داده موقت گردش‌کار — ماژول اشخاص

**حالت:** تأییدشده توسط مالک پروژه در گفت‌وگوی پروژه مورخ ۲۰۲۶-۱۰-۲۹؛ مالک پروژه مسئول امنیت و حریم خصوصی نیز هست.

## تعریف و مالکیت

داده موقت حداقل اطلاعات لازم برای یک گردش‌کار مشخص است که هنوز به هویت پایدار Person متصل نشده است. این داده در staging متعلق به همان ماژول گردش‌کار نگهداری می‌شود، نه در جداول پایدار هویت/تماس/نشانی Persons.

هر رکورد باید حداقل شناسه گردش‌کار، مالک ماژول، هدف، سازنده، زمان UTC ایجاد، زمان UTC انقضا و نسخه سیاست نگهداری را داشته باشد. فقدان هر فیلد ضروری باید ثبت را رد کند.

## قواعد زمانی اجباری

| قاعده | مقدار |
|---|---:|
| TTL پیش‌فرض | ۷ روز از ایجاد |
| حداکثر عمر مطلق | ۳۰ روز از ایجاد، بدون امکان عبور با تمدید |
| تمدید | حداکثر یک‌بار؛ فقط گردش‌کار باز، دلیل و مجوز ثبت‌شده |
| تناوب اجرای پاک‌سازی | حداقل هر ۱۵ دقیقه |
| مهلت پاک‌سازی PII خام و داده مشتق | حداکثر ۳۰ دقیقه پس از انقضا |
| هشدار شکست Worker | حداکثر ۵ دقیقه |

## دسترسی و ارتقا

- در لحظه انقضا، خواندن، ویرایش، export و ارتقا مسدود می‌شوند؛ اجرای دیرهنگام پاک‌سازی دسترسی را باز نگه نمی‌دارد.
- داده موقت در جست‌وجوی سراسری، autocomplete عمومی، گزارش عمومی و فهرست عمومی تکراری‌ها نمایش داده نمی‌شود.
- ارتقا به Person فقط پس از انتخاب صریح شخص موجود یا درخواست ایجاد شخص جدید و اجرای duplicate check انجام می‌شود.
- ایجاد/ادغام خودکار شخص از داده موقت ممنوع است.
- ارتقا و اتصال گردش‌کار باید اتمیک یا با سازوکار بازیابی اثبات‌شده و idempotent باشد؛ پاک‌سازی payload موقت بعد از موفقیت کامل انجام می‌شود.
- نام، شماره، شناسه قانونی یا payload خام در log، audit، metrics یا CI artifact مجاز نیست.

## آزمون و عملیات

- Worker در میزبان API ثبت می‌شود و پاک‌سازی را بلافاصله پس از شروع و سپس هر ۱۵ دقیقه اجرا می‌کند. هر batch تا ۵ تلاش با backoff نمایی ۱، ۲، ۴ و ۸ ثانیه برای خطاهای گذرای شبکه/پایگاه‌داده دارد؛ هر batch تراکنش مستقل و قابل تکرار است.
- هشدار عملیاتی از طریق HTTPS webhook پیکربندی‌شده با کلید `Operations:Alerts:WebhookUrl` ارسال می‌شود. URL فقط در تنظیمات امن محیط استقرار قرار می‌گیرد و نباید در مخزن commit شود. پیام صرفاً شامل نوع رخداد، کد خطای فاقد PII و زمان UTC است. مقصد باید پاسخ موفق HTTP بدهد؛ نبود مقصد یا شکست تحویل، خطای Critical ایجاد می‌کند.
- برای پذیرش SLA پنج‌دقیقه‌ای، محیط استقرار باید URL را پیکربندی کند و پایش/آزمون تحویل end-to-end تا سامانه هشدار را ارائه دهد. CI فقط قرارداد فراخوانی هشدار و retry داخلی Worker را می‌آزماید و به‌تنهایی SLA مقصد عملیاتی را اثبات نمی‌کند.

آزمون‌ها باید ساعت قابل‌کنترل، مرز دقیق زمان انقضا، تمدید دوم، Worker خاموش/ناموفق، retry، PII در index/cache/export، ارتقا تکراری و شکست میانه عملیات را پوشش دهند. پاک‌سازی باید idempotent باشد. شکست پاک‌سازی باید هشدار دهد و داده را همچنان از لایه سرویس غیرقابل‌دسترسی نگه دارد.

## سابقه تصویب

مالک پروژه، این سیاست و مقادیر عملیاتی آن را در گفت‌وگوی پروژه مورخ ۲۰۲۶-۱۰-۲۹ پذیرفته است. مالک پروژه هم‌زمان مسئول امنیت و حریم خصوصی است و مسئول امنیت دیگری تعیین نشده است.

این تصویب، سیاست را تأیید می‌کند؛ اجرای Runtime و آزمون‌های AC-31 تا AC-38 را اثبات نمی‌کند.

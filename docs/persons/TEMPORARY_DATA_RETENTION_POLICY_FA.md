# سیاست عملیاتی داده موقت گردش‌کار — ماژول اشخاص

**حالت:** مالک محصول و مسئول امنیت/حریم خصوصی هر دو توسط مالک پروژه (یک فرد در دو ظرفیت سازمانی) تأیید شده‌اند. این تصمیم به‌صورت خوداظهاری دو‌نقشی ثبت شده و بازبینی مستقل شخص ثالث ادعا نمی‌شود.

## تعریف و مالکیت

داده موقت حداقل اطلاعات لازم برای یک گردش‌کار مشخص است که هنوز به هویت پایدار Person متصل نشده است. این داده در staging متعلق به همان ماژول گردش‌کار نگهداری می‌شود، نه در جداول پایدار هویت/تماس/نشانی Persons.

هر رکورد باید حداقل شناسه گردش‌کار، مالک ماژول، هدف، سازنده، زمان UTC ایجاد، زمان UTC انقضا و نسخه سیاست نگهداری را داشته باشد. فقدان هر فیلد ضروری باید ثبت را رد کند.

## قواعد زمانی اجباری

| قاعده | مقدار |
|---|---:|
| TTL پیش‌فرض | ۷ روز از ایجاد |
| حداکثر عمر مطلق | ۳۰ روز از ایجاد، بدون امکان عبور با تمدید |
| تمدید | حداکثر یک‌بار؛ فقط گردش‌کار باز، دلیل و مجوز ثبت‌شده |
| تناوب اجرای پاک‌سازی | حداقل هر ۱۵ دقیقه |
| مهلت پاک‌سازی PII خام و داده مشتق از مخازن عملیاتی | حداکثر ۳۰ دقیقه پس از انقضا |
| هشدار شکست Worker | حداکثر ۵ دقیقه |

## دسترسی و ارتقا

- در لحظه انقضا، خواندن، ویرایش، export و ارتقا مسدود می‌شوند؛ اجرای دیرهنگام پاک‌سازی دسترسی را باز نگه نمی‌دارد.
- داده موقت در جست‌وجوی سراسری، autocomplete عمومی، گزارش عمومی و فهرست عمومی تکراری‌ها نمایش داده نمی‌شود.
- ارتقا به Person فقط پس از انتخاب صریح شخص موجود یا درخواست ایجاد شخص جدید و اجرای duplicate check انجام می‌شود.
- ایجاد/ادغام خودکار شخص از داده موقت ممنوع است.
- ارتقا و اتصال گردش‌کار باید اتمیک یا با سازوکار بازیابی اثبات‌شده و idempotent باشد؛ پاک‌سازی payload موقت بعد از موفقیت کامل انجام می‌شود.
- نام، شماره، شناسه قانونی یا payload خام در log، audit، metrics یا CI artifact مجاز نیست.

## Replica، Cache، Backup و Restore

- محدودیت انقضا باید در لایه سرویس برای تمام replicaها و مسیرهای خواندن/نوشتن اعمال شود؛ تأخیر replication نباید امکان دسترسی پس از زمان انقضا ایجاد کند.
- cache، search index، export موقت و سایر نسخه‌های مشتق‌شده عملیاتی باید همراه با پاک‌سازی اصلی، حداکثر تا ۳۰ دقیقه پس از انقضا حذف یا غیرقابل‌دسترسی شوند.
- Backup و snapshot ممکن است immutable باشند و حذف فیزیکی رکورد از رسانهٔ backup در همان مهلت ۳۰ دقیقه‌ای تضمین‌پذیر نیست. بنابراین backupها باید رمزگذاری‌شده، با دسترسی محدود و دارای دوره نگهداری حداکثرِ مستند باشند. مقدار دقیق این دوره و روش پایان‌عمر backup باید پیش از پیاده‌سازی عملیاتی توسط مسئول امنیت/حریم خصوصی بررسی و تصویب شود.
- پیش از در دسترس قرارگرفتن سرویس پس از Restore، باید مرحلهٔ اجباری reconciliation اجرا شود: تمام رکوردهای منقضی، حذف‌شده یا فاقد مجوز دسترسی باید دوباره مسدود و از مخازن عملیاتی، replicaها، cacheها و indexها پاک شوند. تا پایان موفق این مرحله، API و workerها نباید ترافیک کاربر بپذیرند.
- Restore نباید بتواند داده منقضی را احیا کند. برای اثبات این موضوع، وضعیت انقضا/حذف با شناسه‌های opaque رکورد و بدون نگهداری payload شخصی در یک ledger پایدار و مستقل از snapshot قابل‌بازیابی ثبت می‌شود؛ این ledger باید در preflight بازیابی اعمال شود.
- اگر ledger در دسترس نباشد، سازگاری آن قابل اثبات نباشد یا reconciliation شکست بخورد، Restore باید fail-closed شود و سرویس تا رفع مشکل غیرفعال بماند.
- هیچ backup یا snapshot نباید به‌عنوان راهی برای دورزدن درخواست حذف یا مهلت انقضا استفاده شود. رسانه‌های backup نیز باید مطابق دوره نگهداری مصوب، منقضی و از چرخه خارج شوند.

## آزمون و عملیات

آزمون‌ها باید ساعت قابل‌کنترل، مرز دقیق زمان انقضا، تمدید دوم، Worker خاموش/ناموفق، retry، PII در index/cache/export، ارتقا تکراری، failure injection، Restore از snapshot قدیمی و عدم احیای داده منقضی را پوشش دهند. پاک‌سازی باید idempotent باشد. شکست پاک‌سازی باید هشدار دهد و داده را همچنان از لایه سرویس غیرقابل‌دسترسی نگه دارد. شکست reconciliation بازیابی باید سرویس را fail-closed نگه دارد.

## ۱. هدف بازبینی

هدف، ارزیابی صحت مرز دامنه و مالکیت داده، قابلیت توسعه، سازگاری قراردادهای بین‌ماژولی، امنیت معماری و امکان تبدیل طراحی به قراردادهای اجرایی قابل آزمون است. این بازبینی، بازبینی کد اجرایی یا تأیید مجوز شروع پیاده‌سازی نیست.

گروه مشاور باید طراحی را با نگاه مستقل بررسی کند و فقط بر مبنای متن همین مخزن و تصمیمات ثبت‌شده نظر بدهد. هیچ artifact یا پیاده‌سازی از پروژه‌های دیگر نباید وارد این ارزیابی یا مبنای اقتباس قرار گیرد.

## ۲. خلاصهٔ معماری پیشنهادی

1. Persons تنها مالک هویت پایدار Party حقیقی/حقوقی است.
2. شناسهٔ بین‌ماژولی `PartyId` از نوع UUIDv7 است؛ شناسه‌های طبیعی فقط attribute حساس‌اند.
3. نقش تجاری، نوع هویت، حساب ورود، مجوز، استخدام و مهارت تکنسین از هم جدا هستند.
4. تماس، نشانی و شناسهٔ رسمی چندتایی، زمان‌مند و دارای سیاست دسترسی مستقل‌اند.
5. مصرف‌کنندگان فقط قرارداد نسخه‌دار را مصرف می‌کنند و قبل از ذخیره/انتقال PartyId در registry ثبت می‌شوند.
6. Scope و مجوز در سمت سرور و در مسیر query/command اعمال می‌شوند.
7. تغییرات دارای optimistic concurrency و تراکنش اتمیک هستند.
8. انتشار رخداد، در صورت نیاز، با transactional outbox و تحویل at-least-once طراحی می‌شود.
9. دادهٔ موقت از Party پایدار جداست؛ ارتقای آن خودکار نیست.
10. merge خودکار ممنوع و اجرای merge تا تکمیل قرارداد همهٔ مصرف‌کنندگان مسدود است.
11. snapshot تاریخی اسناد قطعی با تغییر Party بازنویسی نمی‌شود.
12. هیچ پیاده‌سازی runtime در این PR مجاز یا اضافه نشده است.

| D2-10 | merge | فقط انسانی، پیش‌نمایش و قرارداد کامل همه مصرف‌کنندگان؛ بدون حذف مبدأ | آیا پروتکل Prepare/Validate/Apply/Verify/Recovery و کنترل شکست کامل است؟ |

## ۴. چک‌لیست ارزیابی اجباری

برای هر مورد یکی از این نتایج ثبت شود: **قبول (A)**، **اصلاح لازم (R)**، **رد (X)** یا **نیازمند تصمیم مالک (O)**. برای هر R/X/O، شدت، دلیل، اثر، پیشنهاد اصلاح و معیار آزمون لازم است.

### ۴.۱ دامنه و مدل هویت
- [ ] Party مرجع یگانهٔ هویت حقیقی و حقوقی است.
- [ ] PartyId UUIDv7 تنها شناسهٔ عمومی و بین‌ماژولی است.
- [ ] شناسه‌های طبیعی، تماس و ایمیل به‌عنوان PK/FK بین‌ماژولی استفاده نمی‌شوند.
- [ ] NaturalPerson و LegalEntity از نظر مدل mutually exclusive هستند.
- [ ] نقش‌های تجاری از نوع هویت، IAM و استخدام جدا هستند.
- [ ] نماینده/شرکت رابطهٔ مستقل دارند و هویت نماینده کپی نمی‌شود.

### ۴.۲ مرز مالکیت و لایه‌ها
- [ ] Domain فاقد وابستگی به HTTP، EF Core، WPF، Infrastructure و IO است.
- [ ] Application به abstractionها وابسته است و use caseها را مالک است.
- [ ] Infrastructure تنها محل پیاده‌سازی persistence و adapterها است.
- [ ] Contracts مستقل از مدل داخلی و persistence هستند.
- [ ] API تنها ورودی قابل اعتماد و composition root است.
- [ ] Desktop به DB متصل نمی‌شود و قواعد امنیتی را تکرار نمی‌کند.
- [ ] هیچ مصرف‌کننده‌ای مستقیماً جداول Persons را نمی‌نویسد.
- [ ] data-ownership.md و JSON registry از نظر شناسه/مفهوم/مالک/مصرف‌کننده سازگارند.

### ۴.۳ داده و اعتبار زمانی
- [ ] شناسه رسمی بدون منبع معتبر قید یکتایی سراسری ندارد.
- [ ] تعارض شناسه به بررسی انسانی می‌رود و باعث افشای وجود شخص نمی‌شود.
- [ ] نرمال‌سازی تماس ورودی خام را از canonical جدا می‌کند.
- [ ] ثبت تماس با تأیید مالکیت، ورود و رضایت یکی نیست.
- [ ] نشانی از داده مرجع نسخه‌دار استفاده می‌کند و متن آزاد را پشتیبانی می‌کند.
- [ ] تاریخ اعتبار و تغییرات تاریخی قابل ردیابی‌اند.
- [ ] snapshot اسناد قطعی از تغییرات بعدی Party مستقل است.
- [ ] حذف/ناشناس‌سازی با retention، legal hold و وابستگی اسناد هماهنگ است.

### ۴.۴ قراردادها و سازگاری
- [ ] API contract نسخه‌دار و مستقل از Domain است.
- [ ] PartyId consumer قبل از استفاده در registry ثبت می‌شود.
- [ ] فیلدهای عمومی حداقل‌گرا و PII کنترل‌شده‌اند.
- [ ] pagination/filter/sort محدود و پایدارند.
- [ ] concurrency token opaque است و stale update رد می‌شود.
- [ ] idempotency و retry در فرمان‌ها و رخدادها روشن است.
- [ ] outbox در تراکنش اصلی ثبت و تحویل تکراری قابل تحمل است.
- [ ] تغییر breaking در معنا/Scope/validation/version به ADR و نسخه اصلی نیاز دارد.

### ۴.۵ امنیت و حریم خصوصی
- [ ] deny-by-default و Scope در query/command اعمال می‌شود.
- [ ] مشاهده، جست‌وجو، تغییر، شناسه حساس، export، archive و merge مجوزهای مستقل دارند.
- [ ] پاسخ not-found/forbidden موجب enumeration نمی‌شود.
- [ ] log/trace/error/metrics/artifact حاوی PII خام نیست.
- [ ] rate limit و سقف export/search وجود دارد.
- [ ] audit فقط metadata لازم را نگه می‌دارد و PII را کپی نمی‌کند.
- [ ] مسیر پشتیبان/restore و دسترسی مدیر نیز در مدل تهدید دیده شده است.
- [ ] آزمون منفی برای IDOR، stale token، mass assignment، PII leakage و merge hijack تعریف شده است.

### ۴.۶ داده موقت و ادغام
- [ ] داده موقت از Party پایدار جدا و از جست‌وجوی عمومی پنهان است.
- [ ] ارتقا فقط با فرمان صریح و کنترل مجوز/تکرار انجام می‌شود.
- [ ] انقضا/تمدید/پاک‌سازی و هشدار شکست قابل آزمون است.
- [ ] merge با consumer ناشناخته یا قرارداد ناقص متوقف می‌شود.
- [ ] هیچ merge خودکار بر اساس نام/تلفن/شناسه به‌تنهایی وجود ندارد.
- [ ] merge lineage و راهکار recovery/verification حفظ می‌شود.
- [ ] اسناد تاریخی و ledger بازنویسی نمی‌شوند.

### ۴.۷ آزمون‌پذیری و تحویل
- [ ] هر تصمیم معماری به معیار پذیرش قابل آزمون نگاشت شده است.
- [ ] تست منفی واقعاً CI را fail می‌کند و evidence آن نگهداری می‌شود.
- [ ] CI روی SHA نهایی PR سبز است؛ job در حال اجرا PASS تلقی نمی‌شود.
- [ ] هیچ runtime implementation، endpoint، جدول یا migration در این PR اضافه نشده است.
- [ ] manifest و stage gates با اسناد governance ناسازگار نیستند.

## ۵. طبقه‌بندی یافته‌ها

- **Blocker:** نقض مالکیت هویت، امکان دور زدن Scope/مجوز، امکان نوشتن مستقیم مصرف‌کننده، merge نیمه‌کاره/خودکار، افشای PII حساس، یا ناسازگاری بنیادی با ADRهای پذیرفته‌شده.
- **Major:** تصمیم مبهمی که احتمالاً باعث تغییر اساسی قرارداد/مدل داده می‌شود، نبود کنترل concurrency/idempotency، یا ناسازگاری ownership/consumer registry.
- **Minor:** نقص نگارشی، نام‌گذاری یا جزئیات قابل اصلاح بدون تغییر مدل.
- **Observation:** پیشنهاد بهبود که مانع پذیرش نیست.

8. تأیید اینکه هیچ مجوز پیاده‌سازی از این بازبینی استنباط نمی‌شود.

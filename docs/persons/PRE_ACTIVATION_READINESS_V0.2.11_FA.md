# آمادگی نسخه برای فعال‌سازی ماژول اشخاص — v0.2.11

**نوع بسته:** آماده‌سازی پیش از G1  
**وضعیت مجوز ماژول:** قفل؛ `g1Authorized=false`  
**شاخه کاری:** `work/persons-activation-prep-v0.2.11`

## 1. نتیجه آزمون نصب نسخه قبلی

در 2026-10-30 کاربر نصب‌کننده v0.2.10 را اجرا و برنامه را راه‌اندازی کرد. گزارش کاربر: نصب و اجرای برنامه درست بود و به‌جز پیام Windows با عنوان **Unknown Publisher** ایراد دیگری گزارش نشد.

این پیام به امضای دیجیتال فایل Setup مربوط است؛ مقدار `AppPublisher` در فایل Inno Setup فقط metadata نمایشی است و امضای Authenticode ایجاد نمی‌کند. فایل Setup و EXE برنامه در v0.2.10 امضای ناشر قابل‌اعتماد نداشتند.

## 2. تغییر بسته‌بندی در v0.2.11

زیرساخت امضای اختیاری Authenticode اضافه شده است:

- EXE اصلی برنامه پیش از بسته‌بندی Inno Setup امضا می‌شود.
- EXE نصب‌کننده پس از تولید امضا می‌شود.
- فقط گواهی دارای مجوز **Code Signing** (EKU OID `1.3.6.1.5.5.7.3.3`) پذیرفته می‌شود.
- امضا با SHA-256 و timestamp از نوع RFC 3161 انجام می‌شود.
- SignTool پس از امضا، صحت زنجیره و timestamp را بررسی می‌کند؛ شکست امضا یا verification باعث FAIL شدن build می‌شود.
- PFX موقت و certificateهای موقت واردشده به Store در پایان کار پاک می‌شوند.
- اگر گواهی در دسترس نباشد، build preview با وضعیت صریح `UNSIGNED` ساخته می‌شود و هشدار می‌دهد که Unknown Publisher ممکن است نمایش داده شود. هیچ ادعای امضاشدن در این حالت وجود ندارد.
- در اجرای دستی workflow می‌توان `require_code_signing=true` انتخاب کرد؛ در این حالت نبود گواهی باعث توقف build می‌شود.

### پیکربندی گواهی برای خروجی امضاشده

باید یک گواهی Code Signing از مرجع صدور مورداعتماد Windows تهیه و در مخزن GitHub با مسیر زیر ثبت شود:

`Settings → Secrets and variables → Actions`

دو Repository Secret لازم است:

| نام Secret | محتوا |
|---|---|
| `WINDOWS_CODESIGN_CERTIFICATE_BASE64` | محتوای فایل PFX به‌صورت Base64 |
| `WINDOWS_CODESIGN_CERTIFICATE_PASSWORD` | رمز فایل PFX |

برای ساخت مقدار Base64 روی رایانه امنی که PFX در آن قرار دارد، از PowerShell استفاده شود:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("C:\Secure\MDGsm-CodeSigning.pfx"))
```

PFX، رمز آن و private key نباید به Git، artifact، چت یا فایل‌های سورس وارد شوند. تا زمانی که این دو secret با گواهی معتبر و مورداعتماد تنظیم نشده‌اند، خروجی workflow همچنان unsigned خواهد بود. حتی پس از امضا، هشدارهای SmartScreen مربوط به reputation ممکن است جدا از نمایش نام ناشر باقی بمانند.

## 3. محدوده ماژول اشخاص در این نسخه

v0.2.11 نسخه آماده‌سازی است، نه نسخه فعال‌شده ماژول اشخاص. در این نسخه:

- هیچ Persons business entity، endpoint، DbSet، business table یا Persons migration اضافه نمی‌شود.
- جست‌وجو و افزودن اشخاص همچنان فقط preview و حافظه‌ای است.
- هیچ داده واقعی یا دیتابیس عملیاتی برای ماژول اشخاص خوانده یا تغییر داده نمی‌شود.
- Manifest باید `repositoryStage=G0_PREPARATION_ONLY` و `g1Authorized=false` نگه دارد.

## 4. وضعیت پیش‌نیازهای ورود به G1

| پیش‌نیاز | وضعیت فعلی | معیار بستن |
|---|---|---|
| Windows Release Build و .NET tests | انجام‌شده در CI | build بدون Warning/Error و همه تست‌ها موفق |
| نصب و راه‌اندازی Preview | تأیید کاربر در 2026-10-30 | نصب و اجرای برنامه موفق؛ تنها مورد گزارش‌شده Unknown Publisher بود |
| Authenticode برای بسته انتشار | آماده از نظر pipeline؛ گواهی باز است | تنظیم PFX معتبر در GitHub Secrets و verification موفق |
| PostgreSQL disposable migration gate | انجام‌شده در CI | آزمون فقط روی دیتابیس disposable موفق |
| تصویب سیاست داده موقت | باز | تصویب صریح مالک محصول و امنیت/حریم خصوصی |
| تصویب Merge Contract Checklist | باز | تصویب مالک معماری و مسئولان مصرف‌کننده‌ها |
| Required Status Checks روی main | باز | تنظیم واقعی روی remote و ثبت شواهد |
| آزمون منفی Merge-blocking | باز | PR با check شکست‌خورده عملاً غیرقابل Merge باشد |
| مالک اصلی و جایگزین jobهای CI | باز | ثبت افراد واقعی در `CI_JOB_OWNERS_TEMPLATE.md` |

**G1 تا بسته‌شدن موارد باز بالا شروع نمی‌شود.** موفقیت CI یا تست نصب جایگزین تصویب انسانی یا حفاظت واقعی main نیست.

## 5. مسیر بعد از بسته‌شدن پیش‌نیازها

1. **G1 — قراردادها و مالکیت:** تثبیت قرارداد مفهومی هویت، شخص حقیقی/حقوقی، PersonId، تماس، نشانی، نقش‌های تجاری، تشخیص تکراری و قرارداد مصرف‌کنندگان. این مرحله بدون migration عملیاتی است.
2. **بازبینی طراحی:** تصویب قراردادهای Domain/Application/API، مالکیت داده و قرارداد ادغام.
3. **G2 — طرحواره:** طراحی و اعمال migrationهای نسخه‌دار فقط روی PostgreSQL disposable تازه؛ بدون اتصال به داده واقعی.
4. **مراحل بعدی:** پیاده‌سازی use caseها، endpointها، دسترسی سمت سرور، تست‌های امنیتی و integration طبق دروازه‌های مصوب.

این سند برنامه و وضعیت آمادگی را ثبت می‌کند؛ هیچ شرطی را به‌جای مالک آن تصویب نمی‌کند و هیچ مجوز فعال‌سازی صادر نمی‌کند.

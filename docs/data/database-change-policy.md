# سیاست تغییر دیتابیس و migrationها

## مالکیت و قرارداد

هر تغییر schema باید به یک حوزهٔ مالک در `data-ownership.md` متصل باشد و پیش از ایجاد migration، قرارداد کاربردی و علت تغییر آن نوشته شود. schema برای حل موقت نیاز یک فرم، بدون تعیین مالک داده ساخته نمی‌شود.

## قواعد migration

1. migrationهای اعمال‌شده و منتشرشده تغییر داده یا بازنویسی نمی‌شوند؛ اصلاح با migration جدید انجام می‌شود.
2. هر migration شماره/شناسهٔ یکتا، نام روشن، هدف، پیش‌نیاز و اثر روی داده را مستند می‌کند.
3. migration باید روی دیتابیس disposable تازه از صفر اجرا شود و سپس مسیر ارتقا از نسخهٔ قبلی نیز آزمایش شود.
4. آزمون ناموفق نباید روی دیتابیس دارای اطلاعات ارزشمند اجرا یا با reset خودکار پنهان شود.
5. migration باید اتمیک باشد هرجا PostgreSQL اجازه می‌دهد؛ عملیات غیراتمیک نیازمند runbook بازیابی روشن است.
6. تغییرات داده‌ای باید رفتار null، تکرار، کلید خارجی، یکتایی و حفظ تاریخچه را بررسی کنند.
7. برای اسناد قطعی، اصلاح داده با UPDATE/DELETE بی‌ردپا مجاز نیست؛ مسیر اصلاحی و audit تعریف شود.
8. نام دیتابیس تولیدی MD-Gsm هنوز در این مرحله به‌عنوان تصمیم مستقل تعیین نشده است. نام دیتابیس‌های تست باید یکتا و آشکارا disposable باشد. هیچ نام دیتابیس پروژهٔ دیگر به MD-Gsm منتقل نمی‌شود.
9. migrationهای تست زیر مجوز runtime تولیدی اجرا نمی‌شوند. پیش از انتشار، نقش runtime با حداقل مجوز لازم جداگانه تعریف می‌شود.
10. اجرای migration خودکار و بی‌قید در هر startup برنامه مجاز نیست؛ فرآیند ارتقا باید نسخه‌بندی، گزارش نتیجه و مسیر شکست داشته باشد.

## آزمون اجباری برای تغییرات حساس

- restore/build/test؛ اجرای migration از صفر و ارتقا؛ بررسی FK/unique/check constraints؛ آزمون تکرار درخواست؛ آزمون شکست میان‌راه و rollback/بازیابی؛ تطبیق مانده‌ها قبل و بعد؛ تست مجوز در API؛ و ثبت checksum فایل‌های migration.

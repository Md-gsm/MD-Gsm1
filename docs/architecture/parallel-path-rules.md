# قواعد منع مسیرهای موازی

این قواعد برای بازبینی طراحی، code review و آزمون‌های معماری‌اند.

## پیش از افزودن مدل یا سرویس

1. نام مفهوم را در `data-ownership.md` جست‌وجو کنید.
2. اگر موجود است، قرارداد و مالک همان مفهوم را مصرف کنید؛ مدل دوم با اسم متفاوت مجاز نیست.
3. اگر موجود نیست، ابتدا مالک، شناسه، روابط، قواعد تغییر، منبع حقیقت و مصرف‌کنندگان ثبت شوند.
4. اگر لازم است schema قدیمی تغییر کند، مسیر migration و حفظ ارتباط‌های تاریخی مستند شود.

## الگوهای ممنوع

- یک Person برای مشتری و یک Person دیگر برای همان فرد به‌عنوان کارمند/تأمین‌کننده.
- موجودی جدا برای فروش، خرید یا تعمیرات.
- engine قیمت دوم به‌صورت محلی در یک فرم.
- ثبت جداگانهٔ دریافت/پرداخت برای تسویهٔ همان بدهی.
- محاسبهٔ مستقل سود در ابزارک و گزارش در حالی که یکی از هزینه‌های مرجع را نادیده می‌گیرد.
- سند حسابداری دوم برای اثری که قبلاً به‌صورت اتمیک ثبت شده است.
- کپی‌کردن سوابق عملیات یا پرونده‌ها در زمان آغاز سال مالی.
- مجوز امنیتی که فقط در UI اعمال شود.
- مدل dashboard که خودش ماندهٔ پول، موجودی، بدهی یا درآمد را ذخیره کند.

## آزمون‌های معماری مورد انتظار

- بررسی جهت project reference و نبود چرخه.
- بررسی اینکه هر مفهوم shared در رجیستری مالک داشته باشد.
- بررسی اینکه کاتالوگ شخص/کالا/واحد/فهرست قیمت/صندوق/دفترکل/دفتر موجودی یک مسیر canonical داشته باشند.
- بررسی idempotency برای عملیات ثبت‌شونده و عدم ایجاد سندهای تکراری.
- بررسی اینکه گزارش و ابزارک فقط از قرارداد دادهٔ ماژول مالک استفاده کنند.
- آزمون‌های دسترسی منفی: دست‌کاری شناسه یا افزودن widget نباید دادهٔ غیرمجاز برگرداند.
- آزمون reconciliation بین مانده‌های projection و ledgerهای مرجع.

قبولی build بدون این آزمون‌ها، اجازهٔ اعلام تکمیل ماژول نیست.

# راه‌اندازی خودکار شبکه و HTTPS سرور مرکزی MD-Gsm

## هدف و مرز امنیتی

نصب‌کنندهٔ سرور مرکزی، تنظیمات شبکه را از Windows استخراج می‌کند. مشتری یا مدیر فروشگاه نباید DNS، IP، CIDR، پورت PostgreSQL، گواهی یا رمز دیتابیس را دستی در نرم‌افزار وارد کند.

این فرایند فقط نصب و پیکربندی محلی را آماده می‌کند. اجرای migration، Bootstrap مالک اولیه، فعال‌سازی IdentityAccess/Persons و Go-Live مستقل و خارج از دامنهٔ این نصب‌کننده باقی می‌مانند.

## تشخیص خودکار شبکه

نصب‌کننده فقط رابط IPv4 فعالی را بررسی می‌کند که:
- مسیر پیش‌فرض فعال داشته باشد؛
- پروفایل Windows آن Private یا DomainAuthenticated باشد؛
- نشانی IPv4 قابل استفاده و prefix معتبر داشته باشد.

از میان نامزدها، رابط دارای کمترین مجموع metric مسیر و رابط انتخاب می‌شود. اگر شبکهٔ خصوصی مناسبی پیدا نشود، چند رابط با اولویت یکسان وجود داشته باشند، یا نام DNS دامنه به IP همان رابط resolve نشود، انتخاب راه‌دور انجام نمی‌شود. در این وضعیت API فقط روی 127.0.0.1:5081 با HTTPS محلی گوش می‌دهد؛ Rule ورودی Firewall و فایل اتصال کلاینت ساخته نمی‌شود.

در سیستم Domain-joined، نام کامل DNS فقط وقتی استفاده می‌شود که واقعاً به IP رابط انتخاب‌شده resolve شود. در Workgroup، URL از IP همان رابط و گواهی دارای IP Subject Alternative Name استفاده می‌کند؛ نام NetBIOS به‌عنوان DNS قابل اعتماد فرض نمی‌شود.

## گواهی و کلید خصوصی

نصب‌کننده یک Root CA محصولی RSA-3072 با کلید خصوصی non-exportable در LocalMachine\My ایجاد یا بازیابی می‌کند. فقط گواهی عمومی Root CA در LocalMachine\Root قرار می‌گیرد. گواهی برگ API برای Server Authentication صادر می‌شود و کلید خصوصی آن فقط به NT SERVICE\MDGsmApi حق خواندن دارد.

API هنگام شروع، thumbprint مشخص‌شده را از LocalMachine\My می‌خواند و در صورت نبودن گواهی، ابهام در thumbprint، نبود private key، انقضا، CA بودن گواهی، EKU نامعتبر یا نبود Digital Signature از شروع listener خودداری می‌کند.

کلید خصوصی Root CA و گواهی برگ هرگز در repository، فایل تنظیمات عمومی یا بستهٔ کلاینت قرار نمی‌گیرند. فایل اتصال کلاینت فقط URL و گواهی عمومی Root CA را شامل می‌شود.

گواهی برگ پیش از انقضا تمدید می‌شود و همان Root CA حفظ می‌شود. کار زمان‌بندی‌شدهٔ روزانه وضعیت گواهی و شبکه را بررسی می‌کند. اگر گواهی/نشانی/تنظیم listener تغییر کرده باشد، سرویس API راه‌اندازی مجدد می‌شود. جایگزینی خودکار Root CA انجام نمی‌شود؛ نزدیک‌شدن Root CA به بازهٔ ۱۸۰ روز مانده به انقضا، به‌جای تغییر خاموش اعتماد کلاینت‌ها، نیازمند رویهٔ صریح تعویض Root و جفت‌سازی دوبارهٔ کلاینت‌هاست.

## فایل اتصال و نصب کلاینت

پس از پیکربندی موفق شبکهٔ خصوصی، فایل عمومی اتصال در مسیر زیر ساخته می‌شود:

C:\Users\Public\Documents\MD-Gsm-Client-Connection.mdgsm.json

این فایل باید از سرور به هر کلاینت با رسانهٔ فیزیکی مورد اعتماد یا کانال از قبل احراز‌شده منتقل شود. فایل را از فرستندهٔ ناشناس یا پوشهٔ اشتراکی بدون احراز هویت نپذیرید؛ داشتن گواهی عمومی به‌تنهایی اصالت کانال توزیع را ثابت نمی‌کند.

نصب‌کنندهٔ Client فایل را دریافت می‌کند، thumbprint و محتوای گواهی عمومی را بررسی می‌کند، Root CA را در LocalMachine\Root ثبت می‌کند و سپس با اعتبارسنجی عادی سیستم‌عامل به مسیر /health/live از طریق HTTPS وصل می‌شود. اعتبارسنجی TLS هرگز غیرفعال نمی‌شود. تنها پس از پاسخ معتبر، Api:BaseUrl در تنظیمات همان کلاینت ثبت می‌شود. Client هیچ API service، PostgreSQL یا credential دیتابیس نصب نمی‌کند.

برای نصب silent، متغیر محیطی MDGSM_CLIENT_CONNECTION_FILE باید به مسیر همان فایل اتصال معتبر اشاره کند.

## Windows Firewall و PostgreSQL

در حالت راه‌دور، تنها TCP/5081 برای برنامهٔ API باز می‌شود و Rule به این موارد محدود است:
- IP محلی رابط منتخب؛
- CIDR همان شبکه؛
- نام رابط شبکهٔ منتخب؛
- پروفایل Private یا Domain؛
- فایل اجرایی API؛
- عدم عبور Edge Traversal.

اگر Rule ساخته نشود، نصب‌کننده به HTTPS loopback بازمی‌گردد و دسترسی راه‌دور را فعال نمی‌کند.

PostgreSQL به 127.0.0.1 محدود می‌ماند. هیچ Rule شبکه‌ای برای PostgreSQL ایجاد نمی‌شود و کلاینت‌ها هرگز مستقیم به PostgreSQL متصل نمی‌شوند.

## پایداری IP و محدودیت شبکه

در Workgroup، آدرس کلاینت از IP رابط سرور استفاده می‌کند. نصب‌کننده تنظیمات DHCP روتر یا IP سیستم را تغییر نمی‌دهد. برای جلوگیری از تغییر نشانی سرور، مدیر شبکه باید در روتر یک DHCP reservation برای سرور ایجاد کند یا آدرس ثابت سازمانی را از قبل در Windows پیکربندی کند.

اگر آدرس IP یا نام DNS سرور تغییر کند، کار روزانهٔ شبکه، نشانی و فایل اتصال جدید را می‌سازد و listener را به‌روزرسانی می‌کند؛ کلاینت‌هایی که URL قبلی را ذخیره کرده‌اند باید فایل اتصال جدید را از کانال معتبر دوباره وارد کنند. این رفتار fail-closed است و به‌جای پذیرش هر گواهی یا تغییر خودکار DNS، نیاز به جفت‌سازی مجدد را آشکار می‌کند.

این پیکربندی شبکهٔ محلی Private/Domain را پوشش می‌دهد. اتصال از بیرون شبکه باید از VPN یا مسیر سازمانی امن استفاده کند؛ بازکردن API روی اینترنت عمومی یا بازکردن PostgreSQL در اینترنت پشتیبانی نمی‌شود.

## شواهد آزمون مورد انتظار

CI ویندوز باید موارد زیر را روی runner دورریختنی اثبات کند:
- تشخیص رابط و CIDR و تطبیق دقیق آن با Firewall؛
- اجرای API فقط روی HTTPS و نبود listener قدیمی HTTP؛
- پاسخ موفق دو کلاینت هم‌زمان؛
- ورود Root CA عمومی و اعتبارسنجی hostname در Client؛
- رد HTTP downgrade، گواهی X.509 خراب/منقضی، گواهی نامتناسب با hostname، issuer غیرمعتبر و endpoint قطع‌شده؛
- رد گواهی API منقضی یا thumbprint ناموجود پیش از بازکردن listener؛
- حفظ PostgreSQL loopback-only و عدم تغییر DB secret در نصب کلاینت؛
- عدم باقی‌ماندن Rule شبکه پس از uninstall.

هیچ گواهی، کلید، credential، migration یا تنظیم شبکهٔ واقعی مشتری توسط CI یا این change set ایجاد نمی‌شود.

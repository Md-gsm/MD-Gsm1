## ۱. هدف و جایگاه سند

این منشور مرجع حاکمیتی پروژه MD-Gsm1 است. هدف آن ثابت نگه‌داشتن مسیر توسعه، جلوگیری از دوباره‌کاری، تعارض مالکیت داده، شاخه‌سازی و PRهای غیرضروری و تغییر مسیرهای بدون تصویب مالک پروژه است.

این سند برای تمام کارهای جدید و بازبینی تغییرات الزامی است. هیچ فرد، گروه، عامل هوش مصنوعی، ابزار یا گردش‌کار خودکاری مجاز نیست به استناد سلیقه شخصی، سرعت اجرا، نظر شفاهی اعضای تیم یا متن یک PR، مفاد آن را نادیده بگیرد.

**تصمیم مستقیم مالک پروژه بر همه پیشنهادها و برداشت‌های دیگر مقدم است؛ اما تا زمانی که مالک سند را صریحاً اصلاح نکرده باشد، نسخه ثبت‌شده همین منشور معتبر است.**

## ۲. مالکیت سند و کنترل تغییرات

1. تنها مالک پروژه با حساب GitHub برابر با @Md-gsm اختیار اصلاح متن این سند را دارد.
2. پیشنهاد اصلاح را سایر اعضای تیم می‌توانند در قالب Issue یا پیشنهاد جداگانه ثبت کنند؛ اما حق تغییر مستقیم فایل منشور را ندارند.
3. هر Pull Request که فایل این منشور را تغییر دهد باید توسط حساب @Md-gsm ایجاد شده باشد. کنترل خودکار پروژه با نام project-charter-owner-gate این شرط را بررسی می‌کند.
4. فایل منشور در CODEOWNERS فقط به @Md-gsm واگذار شده است.
5. تغییر متن، حتی اصلاح نگارشی یا تغییر شماره نسخه، بدون دستور صریح مالک پروژه ممنوع است.
6. سکوت، عدم اعتراض، سبزشدن CI، تأیید یک بازبین دیگر یا ادغام یک PR دیگر به‌منزله اجازه اصلاح منشور نیست.
7. هر اصلاح مصوب باید نسخه، تاریخ، دلیل و خلاصه تغییر را در تاریخچه Git حفظ کند. نسخه قبلی نباید بی‌ردپا حذف یا بازنویسی شود.

**کنترل فنی:** گردش‌کار مالک‌محور در مخزن اضافه شده و اسکریپت حفاظت شاخه اصلی برای الزامی‌کردن check مربوط به آن به‌روزرسانی شده است. برای مسدودشدن قطعی ادغام، check با نام project-charter-owner-gate باید در تنظیمات حفاظت شاخه main به‌عنوان Required Status Check فعال باشد. وضعیت تنظیمات فعلی GitHub از اتصال مدیریتی در دسترس این اجرا قابل خواندن یا تغییر نبود؛ بنابراین تا تأیید این تنظیم، کنترل خودکار آماده است اما اعمال نهایی branch protection هنوز باید راستی‌آزمایی شود.

## ۳. سلسله‌مراتب اسناد و تصمیم‌ها

ترتیب اعتبار اسناد پروژه به شرح زیر است:

1. این منشور حاکمیت و قواعد الزام‌آور؛
2. تصمیم‌های معماری مصوب و ADRها؛
3. رجیستری مالکیت داده و نقشه وابستگی ماژول‌ها؛
4. قراردادهای نسخه‌دار و مشخصات هر ماژول؛
5. مستندات اجرایی، Issueها، PRها و توضیحات کد.

اسناد پایین‌تر می‌توانند جزئیات را تکمیل کنند، اما نمی‌توانند برخلاف این منشور تصمیم بگیرند. اگر دو سند یا دو قرارداد با هم تعارض داشتند، کار متأثر باید متوقف شود، تعارض ثبت گردد و تا تعیین تکلیف، قاعده این منشور ملاک است. تغییر مالکیت یا استثنای معماری باید به تصمیم ثبت‌شده و دستور صریح مالک پروژه منتهی شود.

## ۴. قوانین قطعی اجرای پروژه

### قانون ۱ ـ جلوگیری از شاخه و PR غیرضروری

- برای هر اصلاح کوچک، شاخه و Pull Request تازه ساخته نمی‌شود.
- اصلاحات هم‌موضوع و هم‌دامنه در شاخه کاری و PR موجود تجمیع می‌شوند.
- شاخه یا PR مستقل فقط با دلیل فنی ثبت‌شده، مانند چرخه انتشار مستقل، مرز امنیتی/مالکیتی متفاوت یا نیاز به بازبینی مستقل مجاز است.
- PRهای مستقل و متفاوت صرفاً برای کم‌کردن تعدادشان ادغام نمی‌شوند.
- پیش از هر تغییر، مسیر شاخه، base، head، وابستگی‌ها، وضعیت CI و دامنه PRهای مرتبط بررسی می‌شود.
- هیچ تغییر یا ادغامی در main بدون مجوز صریح مالک پروژه انجام نمی‌شود.
- تعداد شاخه‌ها و PRها معیار پیشرفت نیست؛ خروجی پذیرفته‌شده و قابل استفاده معیار است.

### قانون ۲ ـ تعیین مالکیت و قرارداد پیش از توسعه

پیش از شروع هر ماژول یا افزودن یک مفهوم مشترک، باید مالک داده، شناسه مرجع، قرارداد مصرف، وابستگی مجاز، قواعد نوشتن، سطح دسترسی و رفتار خطا ثبت شود.

هیچ ماژولی قبل از این تعیین تکلیف حق ساخت جدول، API، مدل یا منطق موازی برای مفهوم متعلق به ماژول دیگر را ندارد.

### قانون ۳ ـ پایان مرحله با تست واقعی

کدنویسی، build موفق یا CI سبز به‌تنهایی به معنی پایان کار نیست. هر مرحله باید شواهد تست واحد، تست پایگاه داده و مهاجرت، تست قرارداد، تست امنیت و تست یکپارچه‌سازی واقعی با ماژول‌های مرتبطِ پیاده‌سازی‌شده را داشته باشد.

اگر یک ماژول وابسته هنوز ساخته نشده است، فقط انطباق قرارداد آینده قابل آزمون است؛ نباید ارتباط واقعیِ اجرا‌نشده ادعا شود. این موضوع مانع فعال‌سازی مستقل ماژولی نمی‌شود که وابستگی اجرایی ضروری دیگری ندارد.

### قانون ۴ ـ استقلال تکمیل و فعال‌سازی ماژول

تکمیل کل ERP پیش‌شرط فعال‌سازی هر ماژول نیست. هر ماژول پس از عبور از معیارهای پذیرش خودش، تست وابستگی‌های واقعی، بازبینی لازم و تأیید صریح مالک پروژه می‌تواند مستقل فعال شود.

برای مثال، ماژول اشخاص نباید منتظر تکمیل انبار، حسابداری، خرید و فروش یا تعمیرات بماند؛ اما باید قراردادهای اتصال آینده را رعایت کند.

### قانون ۵ ـ یک مالک اصلی برای هر داده

هر داده و مفهوم تجاری فقط یک مالک اصلی و یک مرجع حقیقت دارد. سایر ماژول‌ها فقط از طریق شناسه و قرارداد رسمی به آن ارجاع می‌دهند.

Read model یا projection قابل‌بازسازی مجاز است، اما مالکیت مستقل یا منبع حقیقت موازی ایجاد نمی‌کند. هیچ ماژولی نباید داده مرجع ماژول دیگر را مستقیم و خارج از قرارداد تغییر دهد.

### قانون ۶ ـ قرارداد رسمی و وابستگی یک‌طرفه

- ارتباط بین ماژول‌ها باید از قرارداد روشن، نسخه‌دار و قابل تست عبور کند.
- مصرف‌کنندگان به Contracts عمومی وابسته می‌شوند، نه به جزئیات داخلی Domain یا Infrastructure ماژول مالک.
- وابستگی چرخه‌ای ممنوع است.
- ماژول عملیاتی نباید با نوشتن مستقیم در جداول ماژول دیگر، سرویس مالک را دور بزند.
- عملیات بین‌ماژولی وابسته باید در صورت نیاز با Transaction Core اتمیک و قابل تکرار امن اجرا شود.

### قانون ۷ ـ جلوگیری از توسعه زودهنگام و تغییر دامنه

- معماری باید از ابتدا توسعه‌پذیر باشد؛ اما قابلیت‌های همه ماژول‌های آینده از روز اول پیاده‌سازی نمی‌شوند.
- فقط زیرساخت لازم برای نیاز اثبات‌شده ساخته می‌شود.
- تغییر دامنه، ترتیب یا معیار پذیرش مراحل باید مستند و با تأیید مالک پروژه باشد.
- کار نیمه‌تمام با شروع ماژول جدید پنهان یا تمام‌شده اعلام نمی‌شود.

### قانون ۸ ـ استقلال و امنیت پروژه

- MD-Gsm1 پروژه‌ای مستقل است؛ هیچ کد، فایل، ساختار، اسکریپت، migration، schema، باینری یا دارایی اجرایی از پروژه قدیمی RepairDesk وارد یا بازاستفاده نمی‌شود.
- کنترل دسترسی در سمت سرور اعمال می‌شود؛ مخفی‌کردن منو یا کنترل UI مجوز امنیتی نیست.
- اسناد مالی نهایی‌شده با ویرایش مستقیم تغییر نمی‌کنند؛ اصلاح از مسیر سند اصلاحی یا برگشت قابل ردیابی انجام می‌شود.
- migration اعمال‌شده بازنویسی نمی‌شود؛ تغییر بعدی با migration جدید و آزمون سازگاری انجام می‌شود.
- عملیات مالی و موجودی مرتبط باید اتمیک، قابل حسابرسی و دارای کنترل هم‌زمانی باشند.
- پشتیبان‌گیری و بازیابی باید آزمون عملی داشته باشند.
- نرخ‌های قانونی، مالیاتی و پارامترهای متغیر نباید بدون پیکربندی و نسخه‌بندی در کد ثابت شوند.

## ۵. معماری هدف هسته مشترک

هسته مشترک هدف شامل این حوزه‌هاست. این فهرست مرزبندی و مالکیت را از ابتدا تثبیت می‌کند و به معنی الزام به پیاده‌سازی هم‌زمان همه آن‌ها نیست.

| بخش | مسئولیت و مالکیت |
|---|---|
| Platform Core | شناسه‌های مشترک فنی، تنظیمات عمومی، چرخه عمر، پیکربندی و قراردادهای پایه؛ مالک داده تجاری ماژول‌ها نیست |
| Identity & Access | حساب‌های ورود، کاربران نرم‌افزار، نقش‌ها، مجوزها، احراز هویت و نشست‌ها |
| Organization | شعبه‌ها، تعریف انبار، ساختار سازمانی و عضویت/محدوده دسترسی سازمانی |
| Party / Persons | هویت اشخاص حقیقی و حقوقی، PartyId پایدار، نقش‌های تجاری شخص و اطلاعات تماس |
| Audit & Security | رویدادهای ممیزی و امنیتی و سیاست‌های مشترک امنیتی؛ مالک داده تجاری مبدأ نیست |
| Transaction Core | تراکنش اتمیک، کنترل هم‌زمانی، idempotency و هماهنگی عملیات؛ مالک سند تجاری نیست |
| Infrastructure | PostgreSQL، اتصال و پیکربندی زیرساخت، migration، پشتیبان‌گیری و بازیابی |

## ۶. مالکیت یکتای داده‌ها

| اطلاعات | مالک اصلی | مرز مسئولیت |
|---|---|---|
| هویت طرف حساب، شخص حقیقی/حقوقی و PartyId | Persons | مشتری، همکار و تأمین‌کننده نسخه‌های جداگانه هویت نمی‌سازند |
| اطلاعات تماس و نشانی شخص | Persons | سایر حوزه‌ها با PartyId ارجاع می‌دهند |
| حساب ورود، نام کاربری، رمز، نشست و وضعیت کاربر | IdentityAccess | حساب ورود با هویت تجاری شخص یکی نیست |
| نقش امنیتی و مجوز عملیات | IdentityAccess | مهارت یا تخصیص تکنسین مجوز ورود محسوب نمی‌شود |
| شعبه و ساختار سازمانی | Organization | هویت مستقل و وضعیت شعبه در همین حوزه نگهداری می‌شود |
| تعریف انبار و اتصال آن به شعبه | Organization | موجودیت سازمانی انبار از موجودی آن جداست |
| عضویت کاربر در شعبه/انبار و محدوده سازمانی | Organization | IdentityAccess قواعد مجوز را با مصرف این محدوده‌ها اعمال می‌کند |
| کالا، قطعه و خدمت | کاتالوگ کالا و خدمات | یک کاتالوگ مرجع؛ نه کاتالوگ جدا در خرید، فروش و تعمیر |
| موجودی، دفتر گردش، رسید، حواله و انتقال کالا | Inventory | تنها مالک تغییر قطعی موجودی؛ برای انبارهای متعلق به Organization |
| بهای تمام‌شده و ارزش‌گذاری موجودی | سرویس/حوزه ارزش‌گذاری موجودی | محاسبه موازی ناسازگار ممنوع |
| سفارش و فاکتور خرید | Purchasing | Inventory، Treasury و Accounting از قراردادهای رسمی مصرف می‌کنند |
| سفارش و فاکتور فروش | Sales | Inventory، Treasury و Accounting از قراردادهای رسمی مصرف می‌کنند |
| اسناد حسابداری، کدینگ و دفتر کل | Accounting | سایر ماژول‌ها اثر مالی را از قرارداد ثبت می‌کنند |
| دریافت، پرداخت، صندوق، بانک، چک و تسویه | Treasury | هر ماژول منطق پرداخت موازی برای خود نمی‌سازد |
| پرونده تعمیر، پذیرش، مهارت و تخصیص تکنسین | RepairOperations | Persons هویت طرف حساب را می‌دهد و مالک گردش‌کار تعمیر نیست |
| رویداد ممیزی و امنیتی | Audit & Security | ماژول مبدأ همچنان مالک داده تجاری و عملیات خود است |

رجیستری جزئی مالکیت در docs/architecture/data-ownership.md و نسخه ماشینی آن در docs/architecture/data-ownership-registry.json نگهداری می‌شود. این منشور بر آن‌ها حاکم است.

## ۷. اصول اتصال بین ماژول‌ها

1. شناسه مرجع هویت طرف حساب PartyId از نوع UUIDv7 است. شناسه طبیعی یا شماره ملی کلید اصلی ارجاع بین ماژول‌ها نیست.
2. یک شخص می‌تواند چند نقش تجاری داشته باشد؛ برای مشتری، همکار یا تأمین‌کننده شدن، هویت جدید ساخته نمی‌شود.
3. حساب ورود می‌تواند به شخص مرتبط شود، اما IdentityAccess مرجع حساب ورود و امنیت است و Persons مرجع هویت طرف حساب.
4. تعریف Branch و Warehouse در Organization است؛ ثبت موجودی، گردش و انتقال در Inventory است.
5. Accounting فقط مالک دفتر کل و سند حسابداری است؛ Sales/Purchasing مالک سند تجاری است و Treasury مالک دریافت/پرداخت.
6. RepairOperations مهارت، برنامه‌ریزی و تخصیص تکنسین را مالک است؛ مجوز امنیتی کاربر جایگزین تخصیص دامنه‌ای تکنسین نمی‌شود.
7. هر مصرف‌کننده داده فقط حداقل snapshot تاریخی لازم را در سند خودش نگهداری می‌کند؛ این snapshot هویت یا منبع حقیقت جدید ایجاد نمی‌کند.
8. عملیات چندماژولی باید در برابر retry، هم‌زمانی، شکست میانی و ثبت تکراری ایمن باشد.
9. قراردادهای API و رویدادها باید نسخه‌دار، مستند و دارای تست سازگاری باشند.

## ۸. معیار پایان و وضعیت مراحل

هر مرحله فقط با تمام‌شدن دامنه مصوب، تست‌های موفق، شواهد قابل بازبینی، نبود مانع بحرانی/امنیتی و تأیید پذیرش بسته می‌شود.

وضعیت‌های رسمی:
- شروع‌نشده
- در حال اجرا
- متوقف به دلیل مانع
- آماده بازبینی
- تست‌شده
- پذیرفته‌شده
- فعال

تست‌شده، پذیرفته‌شده و فعال سه وضعیت مجزا هستند. موفقیت build یا CI به تنهایی هیچ‌یک از دو وضعیت آخر را ایجاد نمی‌کند.

حداقل شواهد پذیرش:
- build و تست واحد؛
- تست یکپارچگی واقعی با PostgreSQL و migrationهای تازه و ارتقا؛
- تست API و قراردادهای نسخه‌دار؛
- تست اتصال واقعی با ماژول‌های مرتبطِ موجود؛
- تست امنیت مثبت و منفی و کنترل دامنه داده در سمت سرور؛
- تست هم‌زمانی، retry و عملیات تکراری؛
- تست نصب، backup و restore در صورت شمول مرحله؛
- نتیجه بازبینی مستقل، فهرست موانع باقیمانده و تأیید پذیرش مالک پروژه.

## ۱۰. اولویت فعال پروژه

تا زمان پذیرش و فعال‌سازی اشخاص، اولویت توسعه روی موارد زیر متمرکز است:

1. ممیزی واحد و نهایی PRهای مرتبط با Persons و IdentityAccess؛
2. تکمیل قراردادهای مالکیت و اتصال لازم؛
3. تکمیل قابلیت‌های واقعی اشخاص و تست اتصال واقعی آن به IdentityAccess؛
4. برطرف‌کردن موانع تست، امنیت و بازبینی مستقل؛
5. پذیرش و فعال‌سازی مستقل اشخاص.

ساخت ماژول‌های کسب‌وکاری جدید یا توسعه زیرساخت‌های غیرضروری در این بازه اولویت ندارد. هیچ PR فعلی صرفاً برای کم‌کردن تعداد PRها ادغام نمی‌شود؛ PRهای مستقل فقط بر اساس دامنه و وابستگی واقعی تعیین تکلیف می‌شوند.

## ۱۱. الزام برای همه مشارکت‌کنندگان

هر عضو تیم یا دستیار برنامه‌نویسی، پیش از شروع کار باید این منشور، رجیستری مالکیت، نقشه وابستگی و مستندات ماژول هدف را بخواند.

هر پیشنهاد اجرایی یا PR باید حداقل مشخص کند:
- کدام مرحله و کدام معیار پذیرش را پوشش می‌دهد؛
- مالک داده‌های درگیر چه کسی است؛
- کدام قراردادها مصرف یا تغییر می‌کنند؛
- به کدام شاخه و PR موجود وابسته است؛
- چه تست واقعی و چه شواهدی ارائه می‌کند؛
- آیا دامنه یا مالکیت مصوب را تغییر می‌دهد یا خیر.

هر تغییر متناقض، مالکیت موازی، مسیر موازی، ادغام بی‌مجوز، ادعای تست‌نشده یا تغییر منشور بدون اختیار مالک، مغایر قواعد پروژه است و باید پیش از ادغام متوقف و اصلاح شود.

**این منشور تا زمانی که فقط مالک پروژه با دستور صریح آن را اصلاح نکرده باشد، ثابت و الزام‌آور باقی می‌ماند.**
